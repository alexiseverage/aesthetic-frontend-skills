## Analysis

Lotto Scratcher Commerce is application-ready because its strongest signal is a printed, disposable, state-lottery ticket object with a built-in conceal/reveal mechanic. The load-bearing pattern is: drag-based reveal-ticket object model + grey/silver latex scratch material + printed security texture + prize-first dense play grid hierarchy + state-lottery/convenience-store context. Frontend translation should begin with the ticket frame and discrete reveal compartments, then add saturation, bursts, foil simulation, barcode/serial noise, validation box artifacts, and residue/debris as evidence of that object model.

The category is not casino. Even when scratchers use money, vault, or jackpot metaphors, they remain flat retail artifacts organized around denomination, hidden numbers, validation, and purchase-at-counter optimism. Avoid chips, felt, roulette, dealer silhouettes, dark lounge spectacle, and immersive table-game atmosphere; those belong to the sister `casino` entry.

Recommended token direction: use bright retail color roles, display type for prize headlines, tabular or condensed utility type for validation copy, `0–6px` ticket geometry, dense 4px/8px compartments, and motion limited to accessible reveal feedback. For scratch interactions, pointer/touch drag should reveal only the brush path, one click should leave at most a small mark, and completion should require a substantial coverage threshold rather than a boolean clicked state. Accessibility risk is mainly dense microcopy and metallic simulation behind essential text; keep interactive instructions on solid high-contrast plaques and preserve keyboard/button fallbacks.
